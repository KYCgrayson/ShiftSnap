# 班表日曆匯出計畫

## 背景與大目標

使用者在設定中選擇匯出目的地、名稱、顏色、內容、標題和提醒，先看到實際月份與選取筆數摘要，確認後才修改手機日曆。IShift 管理單一班表日曆，改名與改色沿用同一日曆 ID。手機日曆的資料須與帳號擁有權和離線唯讀限制一致。

## 現況與根因

- 設定頁連接時會立即建立日曆並同步；標題、內容、提醒選擇後也會立即持久化和同步，沒有整體確認。
- iOS 建立日曆失敗時可能退到任意個人可寫日曆。已保存的舊 ID 也可能指向這類個人日曆，不能直接改名。
- 日曆、班次、班表審核等畫面在資料編輯後會呼叫 `syncUserShifts`；這些屬於既有連線下的資料更新，設定頁不能再由零散控制元件暗中觸發同步。

## 失敗情境（實作前列出）

1. 使用者取消設定：不建立/更新日曆、不寫事件、不儲存草稿偏好。
2. 名稱空白、過長、權限拒絕、帳號切換或離線唯讀：阻止提交並顯示原因。
3. iOS 所有來源拒絕新日曆：顯示無法建立；不能退回任意個人日曆。
4. 舊目的地 ID 指向個人日曆：不能暗中改其名稱或顏色；預設建立專屬 IShift 日曆，只有明示整本日曆影響並確認沿用後才可修改。
5. 日曆改名/改色後 OS 讀回不符或更新失敗：告知未完全套用，不宣稱成功。
6. 同步部分事件失敗：顯示部分失敗；不能把選取筆數說成新增筆數。
7. 篩選變更移除先前 IShift 管理事件：確認摘要需預告可能移除。
8. 無班次的月份仍可確認，但須清楚顯示選取 0 筆與可能清理舊管理事件。

## QA 與通過標準

- 取消與離線情境中，原生 create/update/delete event/calendar 呼叫均為 0，草稿偏好不變。
- 確認後建立一個專屬日曆；後續改名改色讀回同一 ID，顏色與名稱和選擇相符。
- 摘要準確列出目的地、名稱、顏色、月份、篩選、**選取**筆數、標題、提醒與可能清理的管理事件。
- 改變內容、標題、提醒不會透過舊設定控制項繞過確認；既有班次編輯後同步保留帳號擁有權與離線限制。
- 原生寫入或讀回不符時呈現真實失敗/部分成功，不誇稱已完成。

## 原生驗收發現的必要修正

QA 啟動在真實 iOS SecureStore 重現：冒號不屬於合法 key 字元。既有離線身份/登出標記常數含冒號，mock storage 未模擬此限制。修正前失敗情境：寫入或刪除標記被拒絕、沒有有效 session 時無法可靠還原離線身份、登出標記不能持久化。將這兩個 SecureStore key 改為點分隔（AsyncStorage keys 不變）；重新驗證同安裝離線冷啟動和登出。舊 key 在原生端本來就無法成功寫入，無可遷移值。
