# IShift 客服與刪除申請：你怎麼收件、回覆、更新進度

## 目前已驗證
2026-11-07 已在正式 Supabase 啟用 Build 15 使用的三個 RPC。兩個專用測試帳號的 10 項正式 HTTP 驗證通過：客服回執、刪除申請、重試同一編號、本人查詢與其他帳號隔離。通知 migration 與 worker 也已部署，本機資料庫 40 項整合驗證通過；部署後再跑 11 項正式狀態檢查通過。有效寄件設定與排程尚未完成，4 封合成通知保持待送、尚未寄信。已確認手機安裝 Build 15，但這不代表實機畫面或郵件收件已驗證。

## 用戶怎麼確認
登入並連線後，在「設定」送出客服問題，成功會顯示案件編號。刪除帳號會先要求確認，成功後顯示案件編號及目前的 30 天處理目標；帳號不會在按下申請時立即消失。

要看刪除申請進度：離開「設定」再進入，App 會重新讀取狀態。點「刪除帳號」可看完整案件編號與狀態。重複點選不會新增同一筆未完成申請。沒有網路、未登入或後端拒絕時，不能把失敗訊息當成已收件。

## 你怎麼收到通知和回覆
新增通知功能的設計是：管理通知寄到 `appai@appai.info`；用戶取得確認信、案件編號，以及刪除申請收到日起 30 天的具體目標日期。狀態真正變更後再寄進度信。**必須完成 Resend 設定、排程與實際收件驗證後，才能把這段視為已上線。**

你可用 iCloud Mail 或手機 Mail 開啟 `appai@appai.info`。客服通知的 Reply-To 指向申請人已驗證的信箱；按「回覆」前核對收件人，寄件人選 `appai@appai.info`。保留案件編號，方便雙方對照。用戶回覆自動信也會寄到此客服地址。

管理通知附上 IShift 專案的 Supabase Table Editor 連結。客服案件可依信中的編號在 `public.support_requests` 比對 `id`。刪除案件則在 `public.account_deletion_requests` 比對 `id`，先查看當下的狀態。待處理通知另附 Authentication → Users 與 Storage 連結，供你核對 `user_id`、盤點共用資料並清理檔案。結案通知只提供案件查閱指引。連結須登入有權限的 Supabase 帳號，並且只放在管理通知中。

郵件與 App 狀態不同：在 Mail 回信不會自動改變 App 的處理狀態，須在受限 Supabase 後台更新。不能只寄「已完成」但沒有刪除資料。

## 在 Supabase 查看案件
開啟 IShift 專案的 Table Editor：

- `public.support_requests`：客服內容、案件 `id`、送出時間與 `user_id`。
- `public.account_deletion_requests`：刪除案件 `id`、狀態與時間；新增通知版本還有 `operator_note`，其中的內容會寄給用戶。
- 在 SQL Editor 執行 `scripts/admin/request-inbox.sql`：同頁列出案件、已驗證聯絡信箱、目標日期、通知是否接受／待送／失敗。這是私有管理資料，不可貼到公開 issue。

| 狀態 | 你何時設定 | 用戶看到的意思 |
| --- | --- | --- |
| `pending` | 系統收到申請時 | 等待處理 |
| `in_progress` | 已開始盤點及處理 | 處理中 |
| `action_required` | 確實需要處理身分確認等必要資訊，填入具體 `operator_note` | 查看帳號信箱的下一步 |
| `completed` | 真正刪除完帳號及應刪資料，完成驗證後 | 已完成 |
| `rejected` | 有明確且可說明的原因，必須填 `operator_note` | 申請未完成，查看說明 |

在 Table Editor 同時修改 `status` 和 `operator_note` 後儲存；只有狀態改變才會新增通知。一般客服對話直接用郵件回覆。不要要求用戶說明刪除動機、寄信或打電話才接受申請；用戶在 App 的確認已構成申請。

## 實際刪除由你處理
對照信中編號與當下狀態，把 `pending` 改為 `in_progress` 後開始處理。依 [帳號刪除操作手冊](account-deletion-operations.md) 先盤點本人資料、原始照片、共享群組及 Apple 登入。先處理共享依賴及刪除該帳號在 `shift-images`、`note-images` 中擁有的檔案，再刪除 Auth 帳號。核對帳號及應刪資料均已清除後，才把案件改為 `completed`。從收到申請起算 30 天是人工處理目標。

新增郵件資料也在刪除範圍：用 `owner_id` 找出 `request_mail.outbox` 中的客服內文、聯絡地址及操作說明，清理舊客服／舊案件的相關資料。當次完成通知需要的聯絡快照先保留，成功寄出後會清理；若寄送失敗則依錯誤排查，確認用戶實際收到完成通知。還須依既定保留政策清理客服郵箱和郵件供應商的案件內容。

## 收不到信時
`pending` 表示尚未送出；`sending` 表示工作程序已取得案件；`sent` 只表示 Resend 接受，不是用戶一定讀到。`failed` 的 `no_verified_contact` 表示沒有已驗證聯絡地址，其他代碼可能是供應商拒絕、暫時故障或重試耗盡。暫時故障會重試；重試耗盡後須由管理者查核，不能任意重設全部佇列造成重複寄信。

先核對 Resend 投遞結果與客服垃圾郵件匣。Apple 隱藏信箱還要確認 Apple Private Email Relay 已登記寄件來源。後端成功收件與郵件故障分開處理，郵件故障不會刪除申請。
